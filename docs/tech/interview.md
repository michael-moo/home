# 面试经验：AI 应用方向资深前端的能力清单

> 本文根据一次面试中考到的技术点整理，目标岗位是“资深前端 + AI 应用（Agent）”方向。内容截至 2026 年 10 月。每节最后附有自测题，答不上来的就是要补的地方。

---

## 总览

| 方向 | 涉及的技术点 | 考察重点 |
| --- | --- | --- |
| **一、Agent 工程** | workflow 与 agentic loop、停止条件、死循环防护、Sub Agent | 能不能自己从零写一个可靠的 Agent |
| **二、上下文工程** | 压缩、摘要、引用回溯、结构化标记、Prompt 缓存 | 长任务里怎么管理有限的上下文窗口 |
| **三、大模型基础** | 注意力机制复杂度、采样参数、MoE 路由 | 知道模型“为什么这样表现”，而不是只会调 API |
| **四、前端深度** | SSR 完整链路、编辑器、RN 跨端、AI Web | 每个方向能不能讲到原理层 |
| **五、底层与基建** | WASM 字节码、BT 协议 | 能不能自己写基础设施，而不只是拼开源库 |
| **六、软能力** | 简历表达、问题解决方式、源码阅读 | 经验年限和实际深度是否匹配 |

## 一、 Agent 工程

### 1. workflow 与 agentic loop 的区别

参考 Anthropic 的文章《Building effective agents》（2024 年 12 月）里的划分：

| | workflow（工作流） | agentic loop（智能体循环） |
| --- | --- | --- |
| **控制流** | 由代码预先写好，LLM 只负责其中某几步 | 由 LLM 在每一轮自己决定下一步做什么 |
| **可预测性** | 高，路径固定 | 低，路径动态 |
| **适合场景** | 步骤明确的任务（翻译 → 校对 → 排版） | 步骤无法提前确定的任务（排查 bug、写代码） |
| **常见模式** | 提示链、路由、并行、编排者-执行者、评估者-优化者 | “思考 → 调工具 → 观察结果”循环 |
| **成本** | 低、可控 | 高，轮数不确定 |

agentic loop 的最小实现：

```ts
interface ToolCall {
  name: string;
  input: Record<string, unknown>;
}

interface ModelResponse {
  text: string;
  toolCalls: ToolCall[];
}

type Message = { role: 'user' | 'assistant' | 'tool'; content: string };

async function runAgent(
  task: string,
  callModel: (messages: Message[]) => Promise<ModelResponse>,
  runTool: (call: ToolCall) => Promise<string>,
  maxTurns = 30,
): Promise<string> {
  const messages: Message[] = [{ role: 'user', content: task }];

  for (let turn = 0; turn < maxTurns; turn++) {
    const res = await callModel(messages);
    messages.push({ role: 'assistant', content: res.text });

    // 停止条件 1：模型不再调用工具，认为任务完成
    if (res.toolCalls.length === 0) {
      return res.text;
    }

    for (const call of res.toolCalls) {
      const result = await runTool(call);
      messages.push({ role: 'tool', content: result });
    }
  }

  // 停止条件 2：达到最大轮数
  throw new Error(`超过最大轮数 ${maxTurns}，任务未完成`);
}
```

> 面试时能说出“什么时候**不该**用 Agent”同样加分：能用 workflow 解决的，就不要上 Agent。

### 2. 停止条件与死循环防护

只靠“模型不调工具就结束”是不够的，生产环境需要多层兜底：

| 类型 | 做法 |
| --- | --- |
| **正常结束** | 模型返回纯文本（`end_turn`），或调用了专门的 `finish` / `submit` 工具 |
| **轮数上限** | `maxTurns`，超出直接终止 |
| **预算上限** | token 总量、费用、总耗时超出就终止 |
| **重复检测** | 同一个工具、同样的参数连续调用 N 次，判定为死循环 |
| **无进展检测** | 连续几轮没有产生新信息（文件没变、测试结果没变） |
| **错误重试上限** | 同一个工具连续失败 N 次后停止重试，把错误交给模型或用户 |
| **人工介入** | 高风险操作（删除文件、提交代码、付款）前暂停，等待用户确认 |

重复检测示例：

```ts
function createLoopDetector(threshold = 3) {
  const recent: string[] = [];
  return (call: ToolCall): boolean => {
    const key = `${call.name}:${JSON.stringify(call.input)}`;
    recent.push(key);
    if (recent.length > threshold) recent.shift();
    return recent.length === threshold && recent.every((k) => k === key);
  };
}
```

### 3. Sub Agent（子智能体）

**是什么**：主 Agent 把一个子任务交给另一个 Agent 去做。子 Agent 有**独立的上下文窗口**，做完只把结果摘要返回给主 Agent。

**为什么需要**：

| 好处 | 说明 |
| --- | --- |
| **上下文隔离** | 子任务中间过程（读了 50 个文件、试错过程）不会污染主 Agent 的上下文 |
| **并行** | 多个互不依赖的子任务可以同时跑 |
| **专业化** | 不同子 Agent 可以配置不同的提示词、工具权限、模型 |

**谁来决定要不要派发子任务**：在 Claude Code 这类工具里，派发子 Agent 本身就是一个**工具**（例如 `Task`）。是否调用、什么时候调用，由模型根据工具描述**自己决定**，和调用“读文件”工具没有区别。所以工具描述写得好不好，直接影响模型会不会用它。

**什么时候不该用**：

- 子任务之间强依赖、需要频繁共享中间状态
- 任务很小，派发的开销比任务本身还大
- 对 token 成本敏感（每个子 Agent 都要重新带一遍系统提示词和背景信息）

### 4. 典型场景：多页 PPT 并行生成

这是 Sub Agent 很适合的场景：每一页相对独立、内容多、可以并行。

```
主 Agent（编排者）
  ├─ 1. 理解需求，生成大纲（每页标题 + 要点）
  ├─ 2. 制定统一的风格规范（配色、字体、版式、语气）
  ├─ 3. 并行派发：
  │     ├─ 子 Agent A：第 1–3 页
  │     ├─ 子 Agent B：第 4–6 页
  │     └─ 子 Agent C：第 7–9 页
  ├─ 4. 收集结果，检查风格是否一致、页面之间是否衔接
  └─ 5. 合并输出
```

| 要点 | 说明 |
| --- | --- |
| **风格一致性** | 风格规范必须作为输入传给每个子 Agent，不能指望它们“默契” |
| **任务说明要完整** | 子 Agent 看不到主 Agent 的对话历史，派发时要写清楚背景、目标、输出格式 |
| **粒度** | 按页或按章节切分，太细会导致开销过大 |
| **汇总校验** | 合并后由主 Agent 或一个“审校”子 Agent 统一检查 |
| **限流** | 并发数受模型 API 速率限制，需要控制 |

## 二、 上下文工程（Context Engineering）

### 1. 为什么需要

上下文窗口有限，而且**越长效果越差**（注意力被稀释，中间部分的信息容易被忽略，常被称为 “lost in the middle”）。上下文工程就是决定“每一轮该让模型看到什么”。

参考 Anthropic 的文章《Effective context engineering for AI agents》（2025 年 9 月）。

### 2. 常用手段

| 手段 | 做法 | 例子 |
| --- | --- | --- |
| **压缩（Compaction）** | 接近上限时，把历史对话总结成摘要，用摘要开启新的上下文 | Claude Code 的自动压缩、`/compact` 命令 |
| **引用回溯** | 上下文里只保留引用（文件路径、ID、URL），需要时再按引用重新读取 | 只记 “`src/a.ts` 第 30 行有 bug”，不保留整个文件内容 |
| **工具结果清理** | 旧的工具返回结果用完就删掉或截断 | 很久之前的 `ls` 结果没必要一直保留 |
| **结构化笔记** | Agent 把进度写进外部文件（如 `TODO.md`、`NOTES.md`），需要时再读 | 长任务中途记录“已完成 / 待做” |
| **按需检索** | 不一次性塞入所有资料，而是给模型搜索工具，让它自己找 | 用 `grep` 查代码，而不是把整个仓库塞进去 |
| **子 Agent 隔离** | 把高消耗的探索任务交给子 Agent，主 Agent 只收摘要 | 见上一章 |

### 3. “压缩服务于交接”

压缩的目的**不是**把内容变短，而是让“下一个接手的人”（新上下文里的自己、或者另一个 Agent）能**无缝继续工作**。

一份好的压缩摘要应该包含：

| 必须保留 | 可以丢掉 |
| --- | --- |
| 用户的原始目标和明确要求 | 寒暄、重复的确认 |
| 已做出的关键决策及原因 | 已被否定的方案的细节 |
| 当前进度：做完了什么、正在做什么、下一步是什么 | 已经成功的工具调用的完整输出 |
| 关键文件路径、函数名、配置项 | 大段代码原文（保留路径即可回溯） |
| 遇到过的错误和解决方法（避免重蹈覆辙） | 中间的试错过程 |
| 用户的偏好和纠正过的反馈 | |

> 检验标准：把摘要交给一个完全没参与过的同事，他能不能直接接着干？

### 4. 结构化标记（XML 标签）

提示词里用 XML 风格的标签把不同类型的内容分隔开，是 Anthropic 官方文档推荐的写法，在 Claude 系列模型上效果尤其明显。

```xml
<instructions>
根据下面的文档回答问题，只用文档里的信息。
</instructions>

<document source="user_manual.pdf">
……文档内容……
</document>

<question>
如何重置密码？
</question>
```

| 作用 | 说明 |
| --- | --- |
| **边界清晰** | 模型能分清哪部分是指令、哪部分是数据，减少把数据当指令执行（也有助于缓解提示词注入） |
| **方便引用** | 指令里可以写“根据 `document` 标签里的内容……” |
| **方便解析输出** | 要求模型把答案放在 `answer` 标签里，代码里用正则提取 |
| **系统注入信息** | Agent 框架常用特定标签在对话中插入系统提醒（例如社区分析中常提到 Claude Code 使用的 `system-reminder` 标签），与用户输入区分 |

### 5. Prompt 缓存

大部分模型服务支持**前缀缓存**：如果这次请求的开头和上次完全相同，这部分就不用重新计算，速度更快、费用更低。

**对上下文设计的影响**：

- 不变的内容放前面（系统提示词、工具定义），变化的放后面
- 不要在系统提示词开头放时间戳等每次都变的内容
- 历史消息只追加、不修改，压缩时会破坏缓存，所以压缩频率要权衡

### 自测题

1. 你的 Agent 压缩时保留了哪些信息？有没有遇到压缩后“失忆”的情况？
2. 引用回溯和压缩有什么区别？各适合什么场景？
3. 为什么推荐用 XML 标签而不是 Markdown 标题来分隔内容？
4. 什么样的上下文改动会导致 Prompt 缓存失效？

## 三、 大模型基础

做 AI 应用不需要会训练模型，但需要理解模型的基本原理，才能解释“为什么上下文越长越慢”“为什么温度调高会胡说”。

### 1. 注意力机制与复杂度

**做什么**：每个 token 计算和其他所有 token 的相关程度（注意力权重），再按权重汇总它们的信息。

```
Attention(Q, K, V) = softmax(Q · Kᵀ / √d_k) · V
```

**复杂度**（序列长度 `n`，向量维度 `d`）：

| 阶段 | 时间复杂度 | 说明 |
| --- | --- | --- |
| **Prefill（处理输入）** | `O(n² · d)` | `Q · Kᵀ` 是 `n × n` 的矩阵，长度翻倍、计算量约翻 4 倍 |
| **Decode（逐个生成）** | 每个新 token 约 `O(n · d)` | 借助 KV Cache，只需拿新 token 的 `Q` 和缓存的所有 `K`、`V` 计算 |
| **显存** | KV Cache 随 `n` 线性增长 | 长上下文的主要瓶颈之一 |

**常见优化**：

| 技术 | 解决什么 |
| --- | --- |
| **KV Cache** | 避免生成每个 token 时重复计算之前的 `K`、`V` |
| **FlashAttention** | 分块计算，减少显存读写；**计算量还是 `O(n²)`**，只是更快、更省显存 |
| **MQA / GQA** | 多个注意力头共享 `K`、`V`，缩小 KV Cache |
| **滑动窗口注意力** | 每个 token 只看附近 `w` 个 token，复杂度降到 `O(n · w)` |
| **线性注意力 / 稀疏注意力** | 从算法上降低复杂度，通常有效果上的取舍 |

**常见误区**：“注意力只做检索，不做推理”。

这个说法不准确。Transformer 每一层都由**注意力**（在 token 之间搬运、组合信息）和**前馈网络 FFN**（对每个 token 自身做非线性变换）组成。推理能力来自**多层注意力和 FFN 的叠加**，不能单独归因于某一部分。可解释性研究里的 “induction head” 就是由多个注意力头配合完成“发现规律并照着续写”的例子，说明注意力不只是简单的查找。

### 2. 采样参数

模型每一步输出的是**所有词的概率分布**（logits），采样决定从中选哪个词。

处理顺序（不同框架可能略有差异）：

```
logits → 重复惩罚 → 除以温度 → top-k 截断 → top-p / min-p 截断 → softmax → 按概率抽样
```

| 术语 | 作用 | 常见取值 |
| --- | --- | --- |
| **Greedy（贪心）** | 每步都选概率最高的词，结果确定 | 等价于温度为 0 |
| **Temperature（温度）** | 调整分布的“尖锐程度”：越低越保守，越高越随机 | 代码 / 抽取 0–0.3，创作 0.7–1.0 |
| **Top-k** | 只保留概率最高的 k 个词 | 40–50 |
| **Top-p（核采样）** | 只保留累计概率达到 p 的最小词集合 | 0.9–0.95 |
| **Min-p** | 只保留概率不低于“最高概率 × p”的词，比 top-p 更能适应分布变化 | 0.05–0.1 |
| **Repetition / Frequency / Presence penalty** | 降低已出现过的词的概率，减少重复 | 按需微调 |
| **Beam Search（束搜索）** | 同时保留多条候选序列，选整体概率最高的，常用于翻译，聊天场景很少用 | |
| **Seed** | 固定随机种子，便于复现（不同服务对可复现性的保证程度不同） | |
| **Logprobs** | 返回每个 token 的对数概率，可以用来估计模型的“置信度” | |

**延伸**：

- **结构化输出 / 约束解码**：在采样时屏蔽不符合 JSON Schema 的 token，保证输出格式合法。
- **投机解码（Speculative Decoding）**：用小模型先猜几个 token，大模型一次性验证，加速生成且不改变输出分布。

### 3. MoE（混合专家）路由

**结构**：把 Transformer 里的 FFN 层换成多个“专家”（多个 FFN）+ 一个**路由器（Router / Gate）**。

| 要点 | 说明 |
| --- | --- |
| **路由粒度** | **token 级、每层独立**：每个 token 在每一层都会被路由器分配给 top-k 个专家 |
| **激活参数** | 总参数大，但每个 token 只激活少数专家，所以推理成本远低于同参数量的稠密模型 |
| **例子** | Mixtral 8x7B：8 个专家选 2 个；DeepSeek-V3：256 个路由专家选 8 个，外加 1 个共享专家 |
| **负载均衡** | 训练时需要额外机制避免所有 token 都挤到少数专家上 |

**常见误区**：把 MoE 理解为“根据用户意图选专家”（比如数学题交给数学专家）。

- MoE 的路由是**模型内部、每个 token、每一层**的，同一句话里的不同 token 可能走不同专家。
- 专家学到的分工通常**不对应人类能理解的领域**，更多是语法、token 类型等层面的模式。
- “根据请求意图选择不同模型”是**应用层的模型路由**（比如简单问题用小模型、复杂问题用推理模型），和 MoE 是两回事。

## 四、 前端深度

### 1. SSR 完整链路

以 React（Next.js / 自研）为例：

| 阶段 | 发生了什么 | 常见问题 |
| --- | --- | --- |
| **1. 请求进入** | Node 服务（或边缘函数）收到请求，匹配路由 | 鉴权、Cookie 转发、灰度 |
| **2. 数据获取** | 服务端请求接口拿到页面数据 | 请求瀑布、超时、接口失败 |
| **3. 渲染** | `renderToString` 或流式的 `renderToPipeableStream` 生成 HTML | CPU 密集，阻塞事件循环；渲染耗时影响 TTFB |
| **4. 注入状态** | 把数据序列化到 HTML 里（如 `window.__INITIAL_STATE__`） | **XSS**：必须转义 `<`、`</script>` 等字符；数据过大导致 HTML 臃肿 |
| **5. 返回 HTML** | 浏览器先显示内容（FCP 早） | CDN 缓存策略、个性化内容不能缓存 |
| **6. 加载 JS** | 下载并执行客户端 bundle | JS 太大导致“看得见但点不了” |
| **7. 水合（Hydration）** | React 复用服务端 DOM，绑定事件，恢复状态 | **水合不匹配**：服务端和客户端渲染结果不同 |
| **8. 可交互** | 后续路由切换走客户端渲染 | 首屏数据和客户端数据重复请求 |

**水合不匹配的常见原因**：

- 渲染时用了 `Date.now()`、`Math.random()`
- 访问了 `window`、`localStorage` 等只有浏览器才有的对象
- 服务端和客户端的时区、语言不同（日期格式化结果不同）
- HTML 结构不合法（如 `p` 里嵌 `div`），浏览器自动修正后和虚拟 DOM 对不上
- 浏览器插件修改了 DOM

**进阶话题**：

| 话题 | 要点 |
| --- | --- |
| **流式 SSR + Suspense** | 先返回页面骨架，数据好了再分块推送，降低 TTFB |
| **选择性水合** | 优先水合用户正在交互的部分 |
| **RSC（React Server Components）** | 服务端组件不发送 JS 到客户端，和 SSR 是不同层面的概念 |
| **ISR / SWR 缓存** | 静态页面定时或按需重新生成 |
| **Islands 架构** | 页面大部分是静态 HTML，只有少数“岛屿”需要水合（如 Astro） |
| **降级** | SSR 失败时降级为 CSR，保证页面可用 |
| **内存泄漏** | 模块级变量在多个请求之间共享，导致数据串号或内存上涨 |

### 2. 富文本编辑器

| 话题 | 要点 |
| --- | --- |
| **基础 API** | `contenteditable`、`Selection`、`Range`、`beforeinput` 事件 |
| **输入法** | `compositionstart` / `compositionend`，中文输入过程中不能打断 |
| **架构** | 数据模型与视图分离：ProseMirror、Slate、Lexical 都是“文档模型 → 渲染 DOM”，而不是直接操作 DOM |
| **协同编辑** | OT（操作转换，Google Docs 早期方案）与 CRDT（如 Yjs，无需中心服务器做转换） |
| **撤销重做** | 基于操作（transaction）记录，而不是 DOM 快照 |

### 3. React Native 跨端

| 话题 | 要点 |
| --- | --- |
| **旧架构** | JS 和原生通过异步 Bridge 传 JSON 消息，频繁通信时卡顿 |
| **新架构** | JSI（JS 直接持有原生对象引用，可同步调用）、Fabric（新渲染器）、TurboModules（按需加载原生模块） |
| **引擎** | Hermes：预编译字节码，启动更快、内存更小 |
| **性能** | 长列表（FlatList / FlashList）、动画放到 UI 线程（Reanimated） |

### 4. AI Web 应用

| 话题 | 要点 |
| --- | --- |
| **流式输出** | SSE 或 `fetch` + `ReadableStream`，逐块渲染 |
| **Markdown 增量渲染** | 每来一块就全量重新解析很慢；代码块、表格没闭合时如何显示 |
| **中断** | `AbortController` 取消请求，服务端同时停止生成以节省费用 |
| **工具调用展示** | 把 Agent 的思考、工具调用、结果分块展示，可折叠 |
| **安全** | 模型输出的 HTML / Markdown 渲染前要做 XSS 过滤 |

## 五、 底层与基建

### 1. WebAssembly 字节码

| 话题 | 要点 |
| --- | --- |
| **执行模型** | **栈式虚拟机**：指令从操作数栈取值、结果压回栈 |
| **文件格式** | 开头是魔数 `\0asm` + 版本号 `1`，后面是若干段（section） |
| **主要段** | type（函数签名）、import、function、table、memory、global、export、start、element、code（函数体）、data（初始数据）、custom（调试信息等） |
| **值类型** | `i32`、`i64`、`f32`、`f64`，以及 `v128`（SIMD）和引用类型 |
| **线性内存** | 一块连续的字节数组，以 64 KiB 为一页，JS 通过 `ArrayBuffer` 读写 |
| **结构化控制流** | 没有任意跳转，只有 `block`、`loop`、`if` 和 `br` 系列，便于快速校验 |
| **文本格式** | WAT，是字节码的可读形式，可以和二进制互相转换 |

一个最小的 WAT 示例：

```wasm
(module
  (func $add (param $a i32) (param $b i32) (result i32)
    local.get $a
    local.get $b
    i32.add)
  (export "add" (func $add)))
```

| 延伸话题 | 要点 |
| --- | --- |
| **工具链** | Emscripten（C/C++）、wasm-pack + wasm-bindgen（Rust）、`wasm-opt` 优化 |
| **JS 互操作成本** | 跨边界调用和数据拷贝有开销，适合“少调用、多计算”的场景 |
| **多线程** | 依赖 `SharedArrayBuffer`，页面需要设置 COOP / COEP 响应头 |
| **WASI** | 让 WASM 在浏览器以外运行（访问文件、网络等系统接口） |
| **WasmGC** | 让 Java、Kotlin、Dart 等带垃圾回收的语言编译到 WASM 更高效 |

### 2. BitTorrent 协议

| 话题 | 要点 |
| --- | --- |
| **种子文件** | `.torrent` 用 Bencode 编码，包含文件信息和每个分片（piece）的哈希 |
| **磁力链接** | 只有 `info hash`，元数据需要从其他节点获取 |
| **找节点** | Tracker 服务器，或 DHT（基于 Kademlia 的分布式哈希表） |
| **下载策略** | 最稀有优先（rarest first），尽快让稀有分片在网络中扩散 |
| **激励机制** | choke / unchoke：优先给上传多的节点传数据（以牙还牙） |
| **浏览器实现** | WebTorrent：浏览器里用 WebRTC 传输 |

### 3. “组合开源方案”与“自己造基建”

两者都有价值，但面试资深岗位时，面试官往往想知道你**能不能在开源方案不够用时自己往下走一层**。

| 层次 | 表现 |
| --- | --- |
| **会用** | 选型合适，能快速把开源库接起来跑通 |
| **会调** | 遇到问题能读源码定位，能改配置、打补丁 |
| **会改** | 能 fork 修改核心逻辑，或给上游提 PR |
| **会造** | 理解原理后能自己写一个简化版（比如手写一个 Agent 循环、一个 Markdown 增量解析器） |

> 建议：从做过的项目里挑 1–2 个方向，至少做到“会改”，最好能讲清楚“如果让我从零实现，我会怎么做”。

## 六、 软能力

### 1. 简历表达

| 问题 | 建议 |
| --- | --- |
| **术语膨胀** | 刚开始做的项目，不要用“生产级”“高可用”“企业级”等词，面试官一追问就露馅 |
| **写清楚角色** | 区分“主导”“参与”“调研”，按实际情况写 |
| **量化结果** | 写可验证的数字：首屏从 3s 降到 1.2s、覆盖 5 个业务线 |
| **每一行都能展开讲 10 分钟** | 写不出细节的条目宁可删掉 |

### 2. 问题解决方式

面试官会观察你是**主动推理**还是**等提示**。遇到不会的深度问题，可以这样回答：

1. **复述问题**，确认理解没有偏差
2. **拆解**：这个问题涉及哪几个环节
3. **提出假设**：我认为最可能的原因是 X，因为……
4. **说出验证方法**：我会通过 Y 来验证
5. **说明边界**：这部分我没有实际做过，但按原理推断应该是……

> 诚实说“不知道”是好的，但最好在“不知道”之后给出推理过程，展示解决问题的能力。

### 3. 源码阅读

“看过源码”在面试里会被追问细节，要有准备：

| 程度 | 能回答的问题 |
| --- | --- |
| **看过解读文章** | 整体架构、核心概念 |
| **浏览过源码** | 主要模块在哪、入口在哪 |
| **逐行读过核心模块** | 关键数据结构、关键函数的执行流程、为什么这样设计 |
| **调试过** | 打断点走过一遍完整流程，能说出调用栈 |

> 只看过解读文章，就说“看过相关分析”；真读过才说“看过源码”，并准备 2–3 个具体细节。

### 4. 广度与深度

| 类型 | 优势 | 风险 |
| --- | --- | --- |
| **应用集成型** | 出活快，能从 0 到 1 落地，技术面广 | 每个方向都浅，难以应对深度追问 |
| **底层钻研型** | 能解决疑难问题，能自己造基建 | 落地速度可能慢 |

资深岗位通常期望 **T 型**：面要广，但至少有一个方向能讲到底层。
